# 콘텐츠 바이블 운영 규칙

상태: `LOCKED`  
상위 정본: `docs/CANONICAL.md`, `docs/GAME_DESIGN_FULL.md`

이 문서는 콘텐츠 위키를 장기적으로 유지하기 위한 내부 규칙이다. 캐릭터·적·스테이지 수가 수백 개로 늘어도 기획과 구현이 서로 다른 버전으로 갈라지지 않게 하는 것이 목적이다.

---

## 1. 한 정보에는 한 정본만 둔다

- 게임 전체 원칙: CANONICAL
- 시스템 공통 규칙: 시스템 상세 문서
- 개별 콘텐츠의 디자인/수치: 콘텐츠 위키
- 실행 데이터: content JSON
- 실행 알고리즘: code

같은 수치를 여러 문서에 복사해 모두 정본으로 취급하지 않는다. 통합 기획서는 중요한 숫자를 요약할 수 있지만, 캐릭터 개별 HP나 스폰 초 단위 값은 위키 페이지로 링크한다.

---

## 2. ID 규칙

ID는 출시 후 저장 데이터와 로그에 연결될 수 있으므로 이름보다 안정적으로 취급한다.

권장 형식:

- 캐릭터: `char_story_militia`, `char_s01_elsia`
- 형태: `char_s01_elsia_f1`, `_f2`, `_f3`
- 적: `enemy_ch1_roadmite`
- 보스: `boss_ch1_gatekeeper`
- 메인 스테이지: `main_01_001` ~ `main_04_020`
- SPECIAL 묶음: `special_gold_convoy`
- SPECIAL 내부 스테이지: `special_gold_convoy_01`
- 이벤트: `event_YYYY_theme`
- 모집 시리즈: `series_01_starlight_order`

표시 이름이 바뀌어도 ID를 함부로 바꾸지 않는다. ID를 바꿀 때는 저장 마이그레이션 여부를 먼저 확인한다.

---

## 3. 상태 전환

`CONCEPT → DESIGN_TARGET → TESTED → LOCKED`

필요하면 `REWORK`, `DEPRECATED`로 빠질 수 있다.

### CONCEPT

- 이름/역할/테마 정도만 존재
- 정확한 데이터 없음
- 구현 금지

### DESIGN_TARGET

- 구현에 필요한 필드가 모두 있음
- 수치는 목표안
- 자동검증/플레이테스트 전

### TESTED

- schema/content validation 통과
- deterministic baseline 통과
- 실제 플레이테스트 완료
- 알려진 문제를 페이지에 기록

### LOCKED

- 현재 릴리스에 들어갈 기준값
- 변경 시 이유와 회귀테스트 필요

---

## 4. 숫자의 종류

페이지에서 숫자는 다음 중 하나로 분류한다.

- `RULE`: 시스템 규칙. 예: 재생산 하한 60F.
- `DESIGN_TARGET`: 테스트 전 목표.
- `TEST_RESULT`: 특정 빌드에서 측정한 결과.
- `LOCKED_VALUE`: 릴리스 기준값.

테스트 전 숫자를 `확정`이라고 쓰지 않는다.

---

## 5. 단위

- 시간 내부 기준: frame/tick 우선. 30F = 1초.
- UI 표시: 초 단위 변환 가능.
- 위치/사거리: sim distance 단위.
- 확률: 0~1 내부값과 % UI 표시를 혼동하지 않음.
- 배율: `×1.25`처럼 기준을 명시.
- HP/공격: 어느 레벨/형태의 값인지 반드시 표기.

예: `Lv1/F1 HP 120`, `attack hit 1 = 80`, `recharge 150F (5.0s)`.

---

## 6. 중복 콘텐츠 검사

신규 캐릭터는 최소 다음과 비교한다.

- 역할이 가장 가까운 기존 3종
- 같은 비용대
- 같은 standing range대
- 같은 속성 대항
- 같은 실루엣 계열

신규 적은 다음과 비교한다.

- 동일 사거리 압박 적
- 동일 속도/HP 역할 적
- 동일 보스 보조 역할 적

신규 스테이지는 다음과 비교한다.

- 같은 적 조합
- 같은 웨이브 리듬
- 같은 보스
- 같은 맵 길이
- 같은 보상

차이가 설명되지 않으면 새 콘텐츠로 만들 이유를 재검토한다.

---

## 7. 상위호환 금지 검사

캐릭터 A가 B보다 다음을 거의 전부 이기면 상위호환 위험이다.

- 더 싸다
- 더 빨리 재생산된다
- HP가 높다
- DPS가 높다
- 사거리가 길다
- 속성 대항이 더 넓다
- 이동/KB가 더 유리하다

고희귀라 해도 5~7개 핵심 축에서 무조건 우위가 되지 않게 한다.

---

## 8. 스테이지 설계와 캐릭터 판매 금지

새 캐릭터가 없으면 사실상 못 깨는 스테이지를 의도적으로 만들지 않는다.

허용:

- 특정 역할이 유리함
- 특정 속성 대항이 큰 도움
- 여러 대체 캐릭터가 존재

금지:

- 특정 S/SS 한 명이 사실상 필수
- 미보유 시 통계적으로 클리어 불가능
- 픽업 기간에만 해결 가능한 기믹

---

## 9. 아트 사양과 전투 사양 동기화

공격 animation contact frame과 simulation hit frame은 대응표를 가진다.

- 시각보다 판정이 먼저 나감 금지
- 투사체가 도착하기 전에 데미지가 보이는 상태 금지
- 사거리보다 무기/VFX가 명백히 짧거나 긴 경우 수정

아트가 아직 없으면 임시 애니메이션을 최종 사양으로 착각하지 않게 `ART_PENDING`을 기록한다.

---

## 10. 협동/PvP 검토

아군 캐릭터를 설계할 때 반드시 다음을 확인한다.

- 협동에서 두 플레이어가 같은 캐릭터를 가져오면 깨지는가
- 팀 전체 10칸에서 무한 벽 조합이 되는가
- 표준화 PvP에서 레벨 차이가 제거돼도 지나치게 강한가
- 실제 성장 친선전에서 +레벨이 과도한가
- 서버 엔티티 수를 폭증시키는가

---

## 11. 보상 경제 검토

스테이지 보상은 개별 값만 보지 않고 시간당 획득량을 본다.

- 직접 플레이 분당 가치
- 2배속 후 분당 가치
- 소탕권 사용 시 가치
- 보상 충전 1회 가치
- 낮은 단계와 높은 단계의 효율 차이

고난도 단계가 더 효율적이어야 하지만, 초보가 낮은 단계로 정상 성장할 수 있어야 한다.

---

## 12. 변경 기록

`LOCKED` 콘텐츠의 수치가 바뀌면 최소 다음을 남긴다.

- 이전값
- 새값
- 변경 이유
- 어떤 테스트가 실패/성공했는지
- 영향을 받는 스테이지/캐릭터

`밸런스 조정` 한 줄만 남기지 않는다.

---

## 13. 삭제/폐기

폐기한 시스템은 신규 코드와 데이터에서 제거한다.

역사 확인이 필요하면 Git history를 사용한다. 동일 기능의 old/new 데이터 파일을 둘 다 활성 상태로 보존하지 않는다.

---

## 14. 구현 착수 체크

다음 질문 모두 YES여야 한다.

- 상위 정본과 충돌하지 않는가?
- 페이지 상태가 DESIGN_TARGET 이상인가?
- 필수 필드가 모두 있는가?
- 기존 콘텐츠와 차이가 설명되는가?
- 수치 기준 레벨/형태/단위가 명시됐는가?
- 협동/PvP 영향이 검토됐는가?
- 필요한 아트/VFX/SFX 사양이 있는가?
- 테스트 방법이 정의됐는가?

하나라도 NO이면 상세 설계를 먼저 보완한다.
