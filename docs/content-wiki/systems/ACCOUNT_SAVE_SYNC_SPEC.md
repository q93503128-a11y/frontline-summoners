# 계정·게스트·저장·동기화 상세 사양

상태: `DESIGN_TARGET`  
상위: `docs/GAME_DESIGN_FULL.md`, `docs/CANONICAL.md`

이 문서는 게스트 플레이, 로그인, 서버 저장, 게스트 데이터 이전, 동시 접속, 진행 초기화, 계정 삭제를 정의한다. 목표는 사용자가 저장 충돌 때문에 진행을 잃지 않게 하고, 서버/로컬 중 어느 쪽이 정본인지 모호한 상태를 만들지 않는 것이다.

---

# 1. 계정 상태

클라이언트 상태는 다음 셋 중 하나다.

- `GUEST_LOCAL`
- `AUTHENTICATED_ONLINE`
- `AUTHENTICATED_OFFLINE_CACHE`

`AUTHENTICATED_OFFLINE_CACHE`는 이미 로그인한 계정이 일시적으로 서버와 연결되지 않는 상태이며 새 서버 정본으로 확정하지 않는다.

---

# 2. 게스트 플레이

- 로그인 없이 메인/SPECIAL/성장/모집 등 1차 싱글 기능 사용 가능.
- 게스트 핵심 진행은 IndexedDB에 저장.
- 설정 일부는 localStorage 사용 가능.
- 저장 성공 여부를 확인하지 않고 UI에서 `저장됨` 표시 금지.
- IndexedDB 실패 시 같은 탭 session memory fallback은 가능하지만 브라우저 종료 시 사라질 수 있음을 명확히 안내한다.

게스트는 온라인 랭킹/친구처럼 서버 식별이 필수인 기능 진입 시 로그인 요구 가능.

---

# 3. 로그인 방식

1차 후보:

- Google OAuth
- 이메일 인증 링크 또는 이메일+인증코드

비밀번호를 직접 저장하는 자체 인증은 우선순위가 낮다.

로그인 계정은 내부 `accountId`를 사용하고 이메일/닉네임을 저장 ID로 사용하지 않는다.

---

# 4. 로그인 후 정본

`AUTHENTICATED_ONLINE` 상태에서는 서버 저장이 경제/소유권/진행의 정본이다.

서버 정본 대상:

- 메인/SPECIAL 클리어
- 첫 클리어/영구 보상 수령 상태
- 캐릭터 소유
- 기본 Lv/+Lv
- 형태 해금/현재 선택 형태
- 골드/모집 재화/soul_shard/진화재료/소탕권
- 모집 기록에 필요한 최소 통계
- 편성 덱
- 친구/차단
- PvP MMR/티어/시즌 통계
- 이벤트/기록전 최고기록
- 계정 프로필 장식

클라이언트는 서버 응답 없이 희귀 재화를 영구 확정하지 않는다.

---

# 5. 저장 버전

저장 구조는 `schemaVersion`을 가진다.

- 버전 증가는 migration 함수와 함께 한다.
- 과거 버전을 읽고 조용히 필드를 버리지 않는다.
- migration 실패 시 원본을 덮어쓰지 않는다.
- 알려지지 않은 미래 버전을 구버전 클라이언트가 열면 쓰기 금지/업데이트 안내.

migration 테스트에는 최소 최근 3개 실제 버전과 최초 지원 버전을 포함한다.

---

# 6. 쓰기 단위

경제/소유권 변경은 가능한 한 원자적 transaction으로 처리한다.

예: 모집 10회

1. 재화 충분 확인
2. 재화 차감
3. 10개 결과 확정
4. 신규 소유/중복 처리 상태 반영
5. totalPulls 통계 반영
6. 하나의 서버 transaction commit

중간에서 실패해 재화만 빠지거나 캐릭터만 지급되는 상태 금지.

---

# 7. 자동 저장 시점

최소:

- 스테이지 결과 확정 직후
- 성장/진화 완료 직후
- 모집 결과 확정 직후
- 덱 변경 후 debounce 저장
- 설정 변경
- 친구/프로필 변경

전투 중 매 tick 전체 저장 금지.

전투 진입 전 필요한 loadout snapshot은 서버/로컬 진행에서 파생한다.

---

# 8. 게스트 → 로그인 이전

게스트 진행이 있는 상태에서 처음 로그인하면 자동 덮어쓰기 금지.

경우 A: 서버 계정이 비어 있음

- `게스트 진행을 이 계정으로 이전` 기본 제안.
- 이전 전 게스트 snapshot hash/시간/주요 진행 요약 표시.
- 서버 transaction 성공 후 로컬에 migrated marker 기록.

경우 B: 서버 계정에도 진행이 있음

자동 merge 금지.

선택 화면:

- 서버 진행 유지
- 게스트 진행으로 교체
- 취소하고 돌아가기

두 진행의 요약:

- 메인 최고 장/스테이지
- 보유 캐릭터 수
- 주요 재화
- 마지막 저장 시간
- PvP/친구 데이터 존재 여부

`둘을 합치기`는 재화/중복 악용과 상태 충돌이 크므로 1차 기본 기능으로 제공하지 않는다.

---

# 9. 게스트 진행으로 서버 교체

위험 작업이므로 2단 확인.

- 서버 기존 진행을 archive snapshot으로 일정 기간 보관할지 정책 후보.
- 확인 후 게스트 progression을 서버 구조로 migration.
- 친구/계정 식별/PvP 계정 기록은 progression overwrite 대상과 분리.

즉 `진행 교체`가 계정 자체를 새로 만드는 것은 아니다.

---

# 10. 로컬 캐시

로그인 계정도 UI 빠른 부팅용 로컬 cache를 둘 수 있다.

캐시에는:

- 마지막 서버 revision
- 읽기용 진행 snapshot
- 설정

을 저장 가능.

서버 접속 성공 시 서버 revision이 우선.

로컬 캐시가 더 최근 timestamp라는 이유만으로 경제 데이터를 서버에 덮어쓰지 않는다.

---

# 11. revision / 충돌

서버 save는 단조 증가 `revision`을 가진다.

쓰기 요청:

```text
accountId
expectedRevision
mutation
```

서버 revision과 다르면 conflict 응답.

클라이언트는 최신 snapshot을 다시 받고 mutation을 재검토한다.

재화 사용 같은 mutation을 자동 재실행해 이중 차감하지 않는다.

---

# 12. 동시 로그인

같은 계정의 여러 탭/기기 읽기는 허용 가능.

경제 쓰기는 revision으로 충돌 방지.

랭킹전/협동 실시간 세션은 계정당 동시 1개만 허용.

다른 기기에서 실시간 세션을 시작하려 하면:

- 기존 세션 유지
- 새 세션으로 전환

중 하나를 명시적으로 선택하게 할 수 있다.

몰래 기존 경기를 끊지 않는다.

---

# 13. 오프라인 플레이

게스트: 로컬이 정본이므로 가능.

로그인 계정의 완전 오프라인 싱글 플레이를 허용할지는 별도 정책이 필요하다.

1차 안전안:

- 서버 연결 없이 읽기용 도감/편성 확인 가능.
- 경제/스테이지 진행을 만드는 전투는 온라인 계정에서는 연결 필요.

향후 offline mutation journal을 구현하기 전까지 복잡한 양방향 merge를 만들지 않는다.

---

# 14. 진행 초기화

`진행 초기화`와 `계정 삭제`를 분리한다.

진행 초기화:

- accountId 유지
- 로그인 방식 유지
- 친구/차단을 유지할지 선택 정책. 1차 후보: 유지.
- 게임 progression/소유/재화/덱/기록을 초기 상태로 변경.
- PvP MMR은 악용 방지를 위해 단순 초기화 대상에서 제외하거나 별도 정책 필요.

2단 확인:

1. `진행을 초기화합니다`
2. 계정 닉네임 또는 지정 확인 문구 입력

즉시 취소 불가능 작업임을 표시.

---

# 15. 계정 삭제

계정 삭제:

- 인증 계정 연결 제거
- 서버 progression 삭제
- 친구 관계/차단 데이터에서 계정 처리
- PvP 랭킹 공개 식별 제거/익명화 정책
- 법적/보안 로그는 필요한 최소 보존정책에 따름

삭제는 진행 초기화보다 더 강한 별도 메뉴.

2단 이상 확인.

삭제 후 같은 이메일로 재가입하면 새 accountId를 기본으로 한다.

---

# 16. 게스트 데이터 삭제

설정/계정 화면에서:

- `이 기기의 게스트 진행 삭제`

제공.

로그인 서버 계정 삭제와 절대 같은 버튼으로 만들지 않는다.

IndexedDB/localStorage/session fallback을 해당 범위에 맞게 정리한다.

---

# 17. 닉네임

- accountId와 별개.
- 중복 닉네임 허용 가능, 친구 고유코드로 구분.
- 길이/금칙어/제어문자 제한.
- 닉네임 변경 쿨다운 후보.

친구 검색에서 닉네임 하나만으로 잘못된 사용자를 확정하지 않는다.

---

# 18. 친구 코드

- 추측하기 어려운 짧은 영숫자 코드.
- 내부 accountId 직접 노출 금지.
- 대소문자 혼동 문자를 피할 수 있음.

예: `AB7K-4M2Q` 형태 후보.

코드는 필요 시 재발급 정책을 둘 수 있으나 재발급 남용으로 차단 회피가 되지 않게 한다.

---

# 19. 클라이언트 저장 오류 UX

저장 실패 시:

- 성공 체크 표시 금지.
- `저장에 실패했습니다. 다시 시도`처럼 구체 상태 표시.
- 재시도 버튼.
- 네트워크 복구 시 자동 재시도 가능한 mutation만 구분.

모집/재화 결제성 mutation은 결과가 불명확할 경우 먼저 서버 transaction ID를 조회해 중복 실행을 막는다.

---

# 20. 전투 결과 idempotency

각 서버 권위 전투는 `battleId`를 가진다.

보상 확정 요청은 같은 battleId로 두 번 처리되어도 한 번만 지급.

- firstClear
- stage reward
- permanent reward
- PvP MMR

모두 idempotent 처리.

브라우저 새로고침/재전송으로 보상 복제가 생기지 않게 한다.

---

# 21. 모집 idempotency

모집 요청도 `requestId`를 가진다.

서버가 이미 완료한 requestId면 동일 결과를 반환하고 다시 재화 차감하지 않는다.

결과 연출은 클라이언트에서 다시 재생 가능하지만 결과 자체 재추첨 금지.

---

# 22. 기록전 저장

끝없는 전선:

- bestSurvivalFrames
- claimedMinuteMilestones

보스 러시:

- bestBossIndex
- bestClearFrames 후보
- claimedMilestones

신기록 보상은 서버에서 기존 기록과 비교 후 한 번만 지급.

---

# 23. 설정 저장

계정과 동기화 권장:

- 언어
- 주요 접근성
- 연출 스킵 선호

기기별 권장:

- 전체 음량
- 그래픽 품질
- 화면 크기/전체화면

2배속 마지막 선택은 계정/기기 중 어느 쪽인지 UX 테스트 후 확정.

---

# 24. 개인정보 최소화

게임 진행에 필요 없는 개인정보를 수집하지 않는다.

친구에게 노출:

- 닉네임
- 프로필 장식
- 온라인/초대 가능 여부
- 공개 설정한 PvP 정보

이메일/인증 제공자 정보는 친구에게 노출하지 않는다.

---

# 25. 백업/복구 운영 기준

서버 운영 단계에서:

- 정기 DB 백업
- migration 전 백업
- 대규모 경제 패치 전 snapshot

정책 필요.

개별 사용자의 실수 복구를 무제한 고객지원 기능으로 약속하지 않는다.

---

# 26. QA

- 신규 게스트 생성/저장/브라우저 재실행.
- IndexedDB 실패 fallback.
- 빈 서버 계정으로 게스트 이전.
- 기존 서버 진행과 게스트 충돌 UI.
- 진행 교체 중 네트워크 끊김.
- 두 탭에서 동시에 골드 사용.
- 모집 요청 재전송.
- 전투 결과 재전송.
- save schema migration 실패 시 원본 보존.
- 진행 초기화와 계정 삭제 UI가 구분되는지.
- 로그인 상태에서 게스트 삭제가 서버 계정을 건드리지 않는지.
- 랭킹전 동시 로그인 차단.
- 친구 코드가 내부 ID를 노출하지 않는지.
