아래 내용을 새 채팅 첫 메시지로 사용한다.

---

전선소환전 / Frontline Summoners 개발을 이전 채팅에서 그대로 이어서 진행한다.

2. 절대 잃지 말아야 할 현재 방향
==================================================

게임은 브라우저 기반 횡스크롤 소환 전략 게임이다.

핵심 전투 루프:
`보급 → 생산 → 전선 → 사거리 → 공격 프레임 → KB → 재생산 → 적 스폰`

싱글 플레이만으로 완전한 게임이어야 하고, 이후 동일한 30Hz 결정론적 코어를 사용해 2인 협동 / 1v1 / 2v2로 확장한다.

현재 과금 없음.
에너지 제한, FOMO, 필수 RNG 보물작, 중복 강제 성장 금지.

개발자 하네스가 돌아간다고 사용자 테스트를 요청하지 않는다.
게임처럼 보이는 vertical slice가 첫 사용자 테스트 게이트를 통과한 뒤에만 Pages 테스트를 요청한다.

3. 초반 진행
==================================================

신규 계정은 **징집병 1종만 보유**한다.
STAGE 1만 처음 열려 있다.

제1장 기본 캐릭터 합류 순서:

- 시작: 징집병
- ST1: 방벽기사
- ST2: 수렵창병
- ST4: 결투검사
- ST6: 청창대
- ST8: 전투마도사
- ST10: 화염술사
- ST13: 왕실기사
- ST16: 이단주술사
- ST20: 공허현자

**현재 10종은 전체 게임 캐릭터 수가 아니라 기본/핵심 로스터다. 기본 캐릭터는 약 10종이면 충분하다.**

10종 이후 대부분의 캐릭터는 다음으로 확장한다.

- 모집/뽑기
- 특정 스테이지 첫 클리어
- 보스 격파
- 외전
- 이벤트
- 도전 콘텐츠

전체 캐릭터를 자동 지급하거나 전부 뽑기로만 몰아넣지 않는다.

==================================================
4. 캐릭터 외형 — 매우 중요
==================================================

캐릭터는 작은 전투 화면에서도 이름이나 색을 읽지 않고 실루엣으로 구분돼야 한다.

색놀이가 아니라 다음을 적극적으로 다르게 만든다.

- 종족
- 체형
- 키
- 머리/몸 비율
- 팔다리
- 장비 부피
- 무기
- 대표 소품
- 이동 방식
- 공격 자세

사람형 기사 비슷한 것들을 색만 바꿔 수십 종 만드는 것을 금지한다.
사람, 소형 종족, 거구, 비인간형, 골렘/기계, 동물형, 부유형, 괴물형, 탈것형 등 다양한 실루엣군을 세계관 안에서 활용한다.

현재 LuizMelo CC0 7개 아트 패밀리는 프로토타입 개발 에셋이지 최종 캐릭터 다양성의 상한이 아니다.

==================================================
5. 캐릭터 업그레이드 / 진화 — 핵심 미래 시스템
==================================================

현재 캐릭터 자체 레벨/강화/진화는 아직 본격 구현 전이지만 **핵심 메타 시스템**이다.
보물이나 보급소 강화로 대체하지 않는다.

레벨 후보:
- Lv1~50
- HP/기본 공격 중심 완만 성장
- 사거리/비용/선딜/KB 횟수 같은 캐릭터 정체성 수치는 원칙적으로 고정
- Lv30 이후 성장 기울기 완화
- 랭크 PvP Lv30 표준화 후보

### 진화에서 반드시 기억할 것

진화는 같은 그림에 숫자만 오른 버전이 아니다.
진화 시 **외형과 실제 전투 사용감이 달라져야 한다.**

변화 가능 항목:

- 전체 실루엣
- 체형
- 의상/갑옷
- 무기/대표 소품
- Idle / Run / Attack / KB / Death 모션
- 소환 VFX
- 공격 VFX
- 투사체
- 효과음
- HP/공격
- 비용/재생산
- 사거리 구조
- 단일/범위
- 멀티히트
- 속성/전문
- Push/Slow/Freeze/Weaken/Strengthen/Critical/방어관통 등

진화는 완전 상위호환일 필요가 없고 sidegrade/전문화 가능.
이전 형태 재선택 가능 방향.

**단순 색놀이 진화 금지. 진화 전후도 작은 전투 화면에서 구분돼야 한다.**

6. 현재 초반 경제/성HP/이속 방향
==================================================

예전 개발 하네스의 ST1:
- 시작 보급 520
- Lv1 수입 65/s
- 지갑 3000
- 높은 성 HP
- 빠른 이속

이 구조는 폐기됐다.

현재 후보 기본 보급소:

- Lv1 12/s · 최대 1000
- Lv2 20/s · 최대 1400 · 강화비 160
- Lv3 30/s · 최대 1900 · 강화비 260
- Lv4 42/s · 최대 2500 · 강화비 390
- Lv5 56/s · 최대 3200 · 강화비 560
- Lv6 72/s · 최대 4000 · 강화비 760
- Lv7 90/s · 최대 5000 · 강화비 1000
- Lv8 110/s · 최대 6200 · 강화비 1300

Lv1은 의도적으로 희소하지만 Lv2 이상은 투자 가치가 분명해야 한다. 보급소를 강화했는데 단순히 지갑만 커지고 실제 전투 템포가 거의 개선되지 않는 함정 선택을 금지한다.

현재 시작 보급:
- ST1~7: 50 → 110
- ST8: 160
- 이후 단계 상승
- ST19: 280
- ST20: 300

정확한 스테이지별 값은 `content/stages/chapter-01.json`을 우선한다.
ST8은 보급소 투자가 본격적인 선택지가 되는 첫 구간이라 이전 120보다 높은 160으로 조정했다.

ST1:
- 시작 보급 50
- 징집병 비용 50
- 아군 성 900
- 적 성 800
- 징집병 이속 3
- 첫 일반 적 이속 2

돌격 역할만 이속 약 4 수준.

목표는 ‘초반부터 돈이 넘치지 않는다’이지 ‘아무것도 못 하고 기다리기만 한다’가 아니다.
따라서 시작 보급, 기본 수입, 처치 보급, 유닛 비용, 적 웨이브, 맵 길이를 함께 감사한다.

현재 deterministic baseline은 로스터 순환, 압박 시 즉시 가능한 강한 증원, 보급소 단계 투자를 함께 사용한다.
ST8 이후에는 강화비를 내고도 최소 방어 병력 한 기 비용을 남길 수 있을 때 첫 보급소 선투자를 허용한다. 이후 추가 강화는 실제 배치와 경쟁해야 한다.

==================================================

질문만 하거나 계획만 길게 쓰고 멈추지 말고 실제 작업을 진행한다.

우선순위:

1. 최신 remote main 재확인.
2. 최신 `CANONICAL / GAME_DESIGN_FULL / IMPLEMENTATION_STATUS / DEVELOPMENT_RULES` 읽기.
3. 현재 3차 경제/웨이브 수치로 ST1~20 deterministic baseline을 합법 순차 해금 상태에서 전수 검증. 특히 ST9·13~20과 ST19/20 보스 실등장을 확인.
4. 실패 구간이 있으면 성 HP를 다시 무식하게 올리거나 새 핫픽스를 덧씌우지 말고 **수입·처치 보급·웨이브·비용·맵 길이와 기존 레거시 경로**를 같이 감사한다.
5. GitHub Actions의 실제 typecheck/test/build 상태를 가능한 범위에서 직접 확인.
6. Cloudflare Pages 배포에 문제가 있으면 수정.
7. 캐릭터 발 위치/그림자/거점 상대크기/모바일 가독성 등 첫 테스트 게이트 감사.
8. 첫 수동 테스트 게이트를 통과하기 전에는 사용자에게 Pages 테스트를 요청하지 않는다.

- 모집/스테이지/보스/외전 획득 구조
- 10칸 수동 편성

13. 작업 방식
==================================================

- GitHub `main`을 정본으로 사용한다.
- 임시 브랜치/PR 중심으로 돌리지 말고 실제 main 상태를 계속 확인한다.
- 변경 전 관련 정본과 `docs/DEVELOPMENT_RULES.md`를 읽는다.
- 자동 검사만 믿지 말고 코드/데이터/UI 구조를 수동 감사한다.
- 수치 변경은 한 수치만 고립해서 보지 말고 경제/맵/웨이브/유닛 비용과 함께 본다.
- 이미 구현된 시스템을 새로 만들지 말고 먼저 현재 코드를 확인한다.
- **새 수정으로 옛 구현을 덮어 가리지 않는다.** 같은 기능의 구식 hotfix/override/중복 함수/죽은 분기/낡은 테스트가 있으면 원인을 확인하고 즉시 제거·통합하여 정본 경로 하나만 남긴다.
- 일회성 진단 workflow/결과 파일은 결과 회수 후 즉시 삭제하고 정본 문서에 필요한 결론만 남긴다.
- 코드와 문서가 다르면 둘 다 맞춘다.
- 이미지 생성 도구는 사용자가 명시적으로 이미지 생성을 요청한 경우에만 사용한다. 게임 개발 중 아트 언급만으로 이미지 생성을 시작하지 않는다.
- 사용자에게 불필요한 선택 질문을 반복하지 말고 합리적인 개발 판단은 직접 내린다.
- 현재 작업을 끝낼 수 있는 범위까지 실제로 진행한 뒤 결과를 보고한다.

==================================================
14. 첫 사용자 테스트 게이트
