2. 제품 핵심
==================================================

브라우저 기반 횡스크롤 소환 전략 게임.

핵심 루프:
`보급 → 생산 → 전선 → 사거리 → 공격 프레임 → KB → 재생산 → 적 스폰`

- 30Hz 결정론적 공용 전투 코어.
- 싱글만으로 완전한 게임이어야 함.
- 이후 같은 코어로 2인 협동 / 1v1 / 2v2.
- 현재 과금 없음.
- 에너지/FOMO/필수 RNG 보물작/중복 강제 성장 금지.
- 판타지 약 40 + 개그/괴상함 약 60.
- 캐릭터별 액티브 버튼 남발 금지. 직접 개입은 소환·보급소·장착 거점 병기 중심.

==================================================
4. 스테이지 시스템 — 매우 중요
==================================================

초기 정밀 기획에서 통합 과정 중 축약됐던 설계가 `docs/STAGE_SYSTEM_DESIGN.md`로 복원되어 있다. 다시 단순 20개 캠페인만 있는 게임으로 축소하지 않는다.

### 두 콘텐츠 축

- `PROGRESSION` = 진도 스테이지
- `SPECIAL` = 특수 스테이지

현재 제1장 20개는 첫 진도 캠페인.
진도는 세계 진행·핵심 기능·기본 캐릭터 해금의 뼈대이며 **모두 싱글 클리어 가능**해야 한다.

특수는 메인 진도와 분리된 수집/성장/도전 축:
- 보스/강적
- 외전/이벤트
- 캐릭터 획득
- 진화/특수 재료
- 편성 제한
- 출격 수 제한
- 시간제한/생존
- 러시/연속전
- 속성/역할 도전 등

기본적으로 특수 스테이지를 못 깼다고 다음 메인 진도가 막히게 하지 않는다.

### 난이도

기존 **1~5는 폐기**, 정본은 **1~12**.
현재 제1장 JSON은 입문 장이라 1~9를 실제 사용한다.
ST20 = 9.
10~12는 이후 더 높은 체급의 진도/특수 콘텐츠를 위해 남긴다.

난이도는 단순 적 HP/공격 배율 공식이 아니다.
적 조합, 스폰, 경제, 맵 길이, 사거리, 거점 트리거, 동시 출격 제한, 편성 제한, 특수 규칙을 종합한 체감 가이드다.

### 동시 출격 제한

10칸 편성과 동시 출격 수는 다른 개념이다.

- 10칸 = 가져가는 캐릭터 종류 수
- `playerUnitCap` = 동시에 살아 있는 아군 개체 수
- `enemyUnitCap` = 동시에 살아 있는 적 개체 수

기본값:
- 아군 50
- 적 50

현재 simulation에 실제 unit cap 차단 로직이 있다.
0.0.18부터 클라이언트도 더 이상 50을 별도 하드코딩하지 않고:

`stage.playerUnitCap → 보물 배치한도 보정 → simulation`

경로를 사용한다.
적은 `stage.enemyUnitCap → simulation`.

특수전에서는 아군 한도를 30/20/15/10/5/3/1 등으로 줄일 수 있다.

### 복원된 정밀 DSL

스테이지 데이터는 장기적으로 다음을 조립 가능해야 한다.

- 맵 길이
- 양쪽 거점 HP
- 시작 보급
- 아군/적 동시 출격 한도
- 적 스폰 목록
- 스폰/페이즈 트리거
- 필요한 적 배율
- 보상
- 편성 제한
- 특수 규칙
- 배경/장식 seed

복원된 트리거 목표:
- 시간
- 적/아군 거점 HP 비율
- 특정 적 사망
- 누적 적 처치
- 누적 아군 사망
- 페이즈 완료
- AND / OR 복합 조건

현재 런타임은 시간 `atTick` 기반이 우선이며, 위 확장 evaluator는 아직 후속 구현이다.

복원된 편성 제한 스키마:
- 허용 희귀도
- 최대 희귀도
- 허용 역할
- 생산비 상한
- 필요 유닛 태그
- 금지 유닛 태그
- 최대 편성 종류 수
- 같은 세력만

`specialRules`는 임의 핫픽스 문자열 실행 장치가 아니다. 등록된 deterministic rule ID만 실제 실행하도록 구현한다.

5. 협동 — 최신 확정 결정
==================================================

협동은 단순 장식이 아니라 **어려운 동일 스테이지를 싱글보다 실제로 수월하게 공략할 수 있는 선택지**다.

그러나 UI에 **`협동 권장` 태그를 절대 만들지 않는다.**
그런 표시는 플레이어가 싱글 플레이를 잘못된 선택처럼 느끼게 할 수 있다.

2인 협동 기본:
- 각 플레이어 5칸
- 팀 전체 최대 10종
- 개인 보급
- 개인 보급소
- 개인 생산 쿨다운
- 공유 거점 HP
- 공유 승패
- 공유 거점 병기

협동 난이도 보정은 유지보수를 단순하게 한다.
필요 시 조정 가능한 것은 **딱 세 축**:
- 적 최대 HP
- 적 공격력
- 적 거점 최대 HP

협동 때문에 다음을 바꾸지 않는다:
- 적 이동속도
- 공격주기
- 사거리
- KB 규칙
- 스폰 시점
- 적 수
- 추가 웨이브
- 추가 패턴
- AI

solo/coop용 stage 데이터를 두 벌 만들지 않는다.
정확한 배율은 멀티 구현 후 2인 baseline/플레이테스트로 결정한다. 지금 임의 숫자를 정본으로 고정하지 않는다.

협동이라고 기본 보상을 깎지 않는다.

6. 캐릭터 외형 / 성장 / 진화
==================================================

캐릭터는 작은 전투 화면에서 이름/색 없이 실루엣으로 구분되어야 한다.

적극적으로 다르게 할 것:
- 종족/생물학적 형태
- 체형/키/머리몸 비율
- 팔다리
- 장비 부피
- 무기/대표 소품
- 이동 방식
- 공격 자세

비슷한 인간형을 색만 바꿔 양산 금지.
현재 LuizMelo CC0 7개 아트 패밀리는 프로토타입 개발 에셋이지 최종 다양성 상한이 아니다.

캐릭터 레벨/강화/진화는 아직 본격 구현 전이지만 핵심 메타다.
보물/보급소로 대체하지 않는다.

진화:
- 같은 그림 + 숫자 상승 금지
- 단순 색놀이 금지
- 실루엣/의상/장비/무기
- Idle/Run/Attack/KB/Death
- VFX/투사체/사운드
- 사거리/공격방식/특효/상태효과/비용/재생산 등이 실제로 달라질 수 있음
- sidegrade/전문화 허용
- 이전 형태 재선택 허용 방향

11. 현재 campaign baseline 상태
==================================================

과거 ST20 실패 원인은 보스 HP 자체보다 저보급 경제에 비해 너무 빠른 초반 압박과 단순 baseline의 값싼 유닛 과소비가 겹친 것이었다.

죽은 `STABLE_FRONTLINE_COUNT + selectReadyBossCounter` 전략은 제거했다. 보스 등장 시점에는 이미 전선이 4기 미만이라 실제 ST20에서 한 번도 발동하지 않았기 때문이다.

현재 후반 baseline은 ST16~20에만 적용한다.

- 적이 오기 전 싼 병력 최대 3기로 작은 전선 준비 후 저축
- 실제 5회 배치 후 Lv3 투자 허용
- 강화비가 부족하면 추가 값싼 생산보다 강화비 저축
- 적이 있으면 현재 적 속성/특효/광역 가치/사거리/체력/보급 대기시간을 함께 평가
- 최대 12초 안에 살 수 있는 준비 완료 유닛만 저축 후보
- 전선 0기면 HP/비용 효율이 좋은 즉시 구매 가능 앵커 우선
- 공허현자는 ST20 클리어 보상이므로 제1장 전투 중 절대 사용하지 않음

소스 충실 독립 결정론 재현 결과:
- ST1~15: 기존 각 테스트 제한 안에서 전부 승리
- ST16 약 138.1초 승리
- ST17 약 165.2초 승리
- ST18 약 78.8초 승리
- ST19 약 102.5초 승리 + 황금가면 실제 등장
- ST20 약 411.4초 승리 + 황금가면/철문장군 둘 다 실제 등장

이 독립 재현은 변경 전 과거 ST16~20 기록과 ST20 109.7초 패배를 스폰 수까지 동일하게 먼저 재현하여 현재 simulation 규칙과의 일치를 교차확인했다.

따라서 **소스 충실 결정론 재현 기준으로 ST1~20 합법 baseline은 현재 전부 통과**한다.
단, 실제 `npm test`/GitHub Actions green을 대신한다고 주장하지 않는다.

==================================================
12. 검증 상태 / Actions 주의
==================================================

이전 마지막 실제 완전 검증에서는:
- install 성공
- typecheck 성공
- build 성공
- 당시 테스트 실패는 ST20 campaign baseline 1개

그 이후 stage schema 및 현재 후반 baseline/ST20 페이싱이 추가됐다.
GitHub Actions status가 계속 비어 있어 현재 HEAD의 install → typecheck → test → build 실제 green은 아직 미확인이다.

검증 가능한 실행 환경이 생기면 반드시 다시 돌린다.
Actions 사용량/실행 불가 상황이면 일회성 workflow를 계속 추가해 쓰레기로 남기지 않는다.

==================================================
13. 개발 방식
==================================================

- GitHub `main` 정본.
- 임시 브랜치/PR 중심으로 돌리지 않는다.
- 작업 전 정본/상세문서/상태/개발규칙 재확인.
- 자동 검사만 믿지 않고 코드/데이터/UI 구조 수동 감사.
- 이미 구현된 시스템을 새로 만들기 전에 실제 코드 확인.
- **새 코드로 옛 구현을 덮어 가리지 않는다.**
- 대체된 hotfix/override/중복 함수/죽은 분기/구식 상수/낡은 테스트는 원인을 확인하고 제거한다.
- 같은 책임은 최종적으로 권위 경로 하나만 남긴다.
- 일회성 진단 workflow/result는 결론 회수 즉시 삭제.
- 코드와 문서가 다르면 둘 다 맞춘다.
- 이미지 생성은 사용자가 명시적으로 요청한 경우에만.
- 불필요한 선택 질문 없이 합리적인 개발 판단은 직접 내린다.

==================================================
14. 첫 사용자 테스트 게이트
==================================================

아래가 충족되기 전에는 사용자에게 테스트하라고 하지 않는다.

- 메인
- 20 진도 스테이지 선택
- 편성
- 도감
- 실제 전투
- 결과/보상
- 새 진행 징집병 1종 + ST1만 개방
- 양쪽 거점 HP 가독성
- 보급/비용/쿨다운/보급소/전선포
- 초반 돈 과잉 없음
- 과도한 초반 성 HP 없음
- 전체 이속 과속 없음
- 솔로 일시정지 완전 동작
- 확정 보물 저장/실제 효과
- 맵 시각/길이 차등
- ST19/ST20 보스 실제 등장
- 원거리 hitFrame 시각 동기화
- PC/가로 모바일 가독성
- ST1~20 합법 순차 baseline

campaign baseline은 소스 충실 재현 기준 통과했지만, **실제 CI 재확인과 시각/모바일/배포 감사가 남아 있으므로 아직 사용자 테스트를 요청하지 않는다.**

다음 실제 작업 우선순위:
1. 현재 HEAD의 typecheck/test/build 실행 가능 여부 재확인
2. 7개 맵·거점·캐릭터 발 위치/그림자·UI 가독성 수동 감사
3. PC/가로 모바일 배치 감사
4. Cloudflare Pages 최신 배포 확인
5. 첫 테스트 게이트 전체 충족 시에만 사용자에게 테스트 요청

이 프롬프트에서 멈추지 말고 최신 GitHub `main`을 다시 읽은 뒤 실제 다음 개발 작업을 이어서 진행한다.
