# Frontline Summoners 개발 정리 규칙 v1.0

이 문서는 게임 기획을 대체하지 않는다. 상위 방향은 `CANONICAL.md`, 시스템 규칙은 관련 정밀 문서, 개별 콘텐츠는 `docs/content-wiki/`를 따른다.

## 1. 작업 전 읽기

모든 의미 있는 수정 전에 다음을 확인한다.

1. `docs/CANONICAL.md`
2. 관련 정밀 문서
   - 성장/모집/진화: `GROWTH_RECRUITMENT_DESIGN.md`
   - 스테이지/SPECIAL/협동/PvP: `STAGE_SYSTEM_DESIGN.md`
3. 대상 `docs/content-wiki/` 페이지
4. `FEATURE_COVERAGE_MATRIX.md`
5. `IMPLEMENTATION_STATUS.md`
6. 관련 `content/` JSON
7. 실제 코드/테스트

기억만으로 이미 구현된 기능을 다시 만들지 않는다.

## 2. 의도 정본과 실행값

- 의도 정본: `CANONICAL → 정밀 문서 → content-wiki`.
- 실행값: `content/ → parser/simulation/UI`.
- 둘이 다르면 실행값이 자동으로 정답이 아니다.
- 불일치 원인을 확인해 문서 또는 구현을 고친 뒤 양쪽과 테스트를 함께 맞춘다.
- 같은 수치를 문서, UI, simulation, 별도 상수에서 각각 독립 소유하지 않는다.

## 3. 콘텐츠 제작 순서

1. 위키에 `DESIGN_TARGET` 작성.
2. 기존 콘텐츠와 역할/실루엣/수치 중복 검사.
3. `content/` 작성 또는 교체.
4. schema/parser/simulation 연결.
5. UI/아트/VFX/SFX 연결.
6. 자동 테스트/typecheck/build.
7. 실제 플레이테스트.
8. 위키를 `TESTED` 또는 `LOCKED`로 갱신.
9. 폐기된 구형 데이터/코드/테스트/문구 제거.

## 4. 레거시 청소

- 기능을 교체할 때 같은 책임의 구식 구현, 핫픽스, override, 임시 patch, 중복 데이터 경로를 함께 찾는다.
- 새 코드를 뒤에 덧씌워 옛 코드를 우연히 이기는 방식으로 해결하지 않는다.
- 같은 책임은 최종적으로 하나의 권위 경로만 남긴다.
- 사용되지 않는 함수, 죽은 분기, 옛 상수, 낡은 저장 필드, 이전 천장/희귀도/속성 규칙이 현재 변경과 관련되면 같은 작업에서 제거한다.
- 과거 코드는 Git history가 보존한다. `혹시 나중에`를 이유로 죽은 코드를 본 저장소에 남기지 않는다.
- 임시 호환 계층이 정말 필요하면 역할과 제거 조건을 문서화하고 테스트로 범위를 고정한다.

## 5. 테스트를 속이지 않는다

- 실패 원인을 찾기 전에 HP, 타임아웃, 재시도 횟수를 크게 올려 테스트만 통과시키지 않는다.
- 낡은 테스트가 폐기된 동작을 강제하면 새 코드에 우회 로직을 넣지 말고 테스트를 현재 정본에 맞춘다.
- typecheck/test/build 실패를 삭제/완화로 숨기지 않는다.
- 자동 시뮬레이션은 밸런스 보조 수단이지 실제 사람 플레이테스트 대체물이 아니다.

## 6. 난이도/밸런스 규칙

- 난이도 1~12를 채우기 위해 억지 고난도를 만들지 않는다.
- 1차 완성은 대부분 1~7, 일부 8 정도가 자연스럽다.
- 스테이지 난이도는 정상 해금 시점의 계정으로 테스트한다.
- HP/공격 배율 하나로 난이도를 만든 뒤 숫자만 붙이지 않는다.
- 캐릭터 수치는 DPS만 보지 않고 비용, 재생산, 사거리, 선딜, KB, 이동, 생존, 속성 대응, 전선 밀도까지 함께 본다.

## 7. 멀티 정합

- 싱글과 권위 멀티는 동일 simulation core를 사용한다.
- 협동 전용 복사 스테이지를 양산하지 않고 같은 Stage 정의 + 명시적 coop scaling을 사용한다.
- 협동 보정은 스탯 축만 사용하고 숨은 추가 웨이브/AI를 넣지 않는다.
- PvP 랭킹전 표준화 규칙은 UI와 서버가 같은 값/함수를 사용한다.
- 재접속/이탈/중복 입력/역순 snapshot을 실제 테스트한다.

## 8. 플레이어 화면 개발자 문구 금지

사용자 화면에 다음 종류의 표현이 나오면 릴리스 실패로 취급한다.

- prototype / debug / TODO / temp / test
- 내부 ID (`enemy-boss-iron`, `banner-01` 등)
- 저장/스키마 버전
- 코드 경로/파일명
- `DESIGN_TARGET`, `TESTED`, `LOCKED`
- 구현 사정, 개발자 TMI, 임시 밸런스 설명

미완성 기능은 `미구현` 버튼으로 노출하지 않고 완성 전까지 메뉴/선택지 자체를 숨긴다.

## 9. 플레이 감각 QA

기능 체크만으로 완료 처리하지 않는다. 다음을 실제로 확인한다.

- 버튼 입력 즉시 반응 여부
- 돈 부족/쿨다운/선택 불가 이유가 읽히는지
- 재생산 완료 시점이 명확한지
- 캐릭터/적 실루엣과 공격이 겹쳐도 판독 가능한지
- 기지/화면 밖으로 sprite와 판정이 파고들지 않는지
- 사망/KB/VFX가 실제 판정을 오해하게 만들지 않는지
- 새 캐릭터 획득 후 도감/편성으로 자연스럽게 이어지는지
- 모집 연출이 첫 획득에서는 특별하고 반복에서는 짜증나지 않는지
- 패배 후 재도전 동선이 짧은지
- 2배속/소탕/필터 상태가 합리적으로 기억되는지
- 모바일 손가락과 safe area 때문에 중요한 정보가 가리지 않는지
- PC/모바일 가로 해상도에서 텍스트 잘림/겹침/화면 밖 배치가 없는지

## 10. 수정 후 필수 검색

- 폐기된 필드/ID/상수의 전체 저장소 참조 검색.
- 중복 구현 검색.
- 문서와 content 값 비교.
- 플레이어 노출 문자열에서 개발용 단어 검색.
- 변경된 캐릭터/스테이지의 위키 링크와 구현 경로 확인.

## 11. 금지

- `fix2`, `hotfix-final`, `override-final2` 같은 누적 덧씌우기.
- 정본 함수 뒤에서 같은 책임을 다시 정의하는 구조.
- 옛 코드가 우연히 호출되지 않는다는 이유로 방치.
- 실패한 테스트를 삭제해 성공처럼 보이기.
- 게임 내부에 개발 메모/TMI를 플레이어 설명으로 넣기.
