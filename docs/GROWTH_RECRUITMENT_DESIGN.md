# 전선소환전 — 모집·성장·진화 정밀 기획 정본

문서 상태: **복원된 상세 정본 보조 문서**  
상위 정본: `docs/CANONICAL.md`  
전체 상세본: `docs/GAME_DESIGN_FULL.md`  
필수 기능 감사: `docs/FEATURE_COVERAGE_MATRIX.md`  
실제 구현 상태: `docs/IMPLEMENTATION_STATUS.md`

> 이 문서는 초기 정밀 기획에서 통합 과정 중 축약된 모집(뽑기), 희귀도, 중복, 레벨, 진화, 수동 편성 방향을 복원한다. 모집·성장·진화·수집 덱에 관해서는 `CANONICAL.md`와 충돌하지 않는 범위에서 이 문서가 `GAME_DESIGN_FULL.md`의 축약된 표현보다 우선한다.

## 1. 메타 성장의 위치

전선소환전의 핵심 루프는 전투와 메타 두 축이 함께 돌아가야 한다.

- 전투 축: `보급 → 생산 → 전선 → 사거리 → 공격 프레임 → KB → 재생산 → 적 스폰`
- 메타 축: `콘텐츠 클리어 → 캐릭터 획득 → 레벨/진화 → 덱 재구성 → 더 다양한 콘텐츠 도전`

보물만으로 캐릭터 성장 시스템을 대체하지 않는다. 캐릭터 레벨·진화·모집·수동 덱은 출시 전 핵심 시스템이다.

기본 제1장 10종은 게임 문법을 배우는 무료 캠페인 로스터이며 모집 의존 캐릭터가 아니다.

현재 캐릭터 전투 정의는 무료10 + 모집15 = 25종이므로, **수동10칸 편성은 더 이상 미래 기능이 아니라 현재 필수 연결 대상**이다.

## 2. 희귀도

정본 희귀도:

- C
- B
- A
- S
- SS

`X`가 필요할 경우 **희귀도가 아니라 변칙/특수 태그**로 사용한다.

원칙:

- 희귀도는 절대 성능 순위가 아니다.
- C/B도 저비용, 빠른 재생산, 특정 사거리, 특정 전문성 때문에 후반까지 사용 가치가 있어야 한다.
- S/SS는 단순 HP/공격력 덩어리보다 새로운 역할·사거리·특효·사용감에 가치를 둔다.
- 만능 캐릭터 금지.
- 같은 캐릭터의 진화 form이 희귀도 자체를 바꾸는 구조를 기본으로 삼지 않는다.

---

## 3. 모집 / 뽑기 철학

- 현재 과금 시스템은 없다.
- 모집은 캐릭터 수집과 새로운 전투 문법 공급이 목적이다.
- 캐릭터 획득을 지나치게 막지 않고 **후한 지급과 많은 모집 기회**를 지향한다.
- 기본 10종은 제1장에서 무료 확보한다.
- 일부 신규 캐릭터는 모집이 아니라 보스/외전/SPECIAL/업적 전용으로 남길 수 있다.
- 모든 캐릭터를 가챠에 몰아넣지 않는다.
- 에너지/FOMO/중복 강제 성장/필수 과금 구조를 붙이지 않는다.

## 4. 복원된 기본 모집 확률

| 희귀도 | 확률 |
| --- | ---: |
| C | 30% |
| B | 28% |
| A | 24% |
| S | 13% |
| SS | 5% |

합계 100%.

실제 데이터에서는 permille 정수 `300 / 280 / 240 / 130 / 50`을 사용한다.

보장 A+/S+에서 상위 희귀도끼리 균등 추첨하여 SS 비중을 왜곡하지 않는다. **보장 최소선 이상에서는 원래 희귀도 가중치 비율을 유지**한다.

## 5. 보장 / 천장

- **10연:** A 이상 최소 1개 보장.
- **30연:** S 이상 최소 1개 보장.
- **60연:** 해당 배너 픽업 SS 보장.
- **100연:** 배너 캐릭터 직접 선택권 1회.

원칙:

- 60회 보장은 같은 회차의 10/30회 보장보다 우선한다.
- 100회 선택권은 랜덤 결과를 강제로 바꾸지 않고 별도 권리로 적립한다.
- 배너가 바뀔 때 보장 누적 이월 범위는 여러 배너가 실제 생길 때 데이터/저장과 함께 확정한다. 현재 한 배너 단계에서 임의 규칙을 추가하지 않는다.

## 7. 중복 획득

중복 캐릭터는 버려지지 않는다.

방향:

- 해당 캐릭터 조각
- 공용 성장 재화

또한 조각 교환을 통해 원하는 캐릭터를 직접 선택할 수 있는 경로를 둔다.

중요:

- 중복 횟수가 캐릭터 정상 성능의 필수 조건이 되어서는 안 된다.
- `N돌 필수` 형태로 기본 성능을 잠그지 않는다.
- 중복은 수집 손실감 완화와 직접 교환을 위한 경제 장치가 우선이다.
- 조각 지급량/교환비/공용 재화 수치는 전체 보상 경제가 준비되기 전에 임의로 확정하지 않는다.

현재 구현은 신규/중복 판정까지이며, 조각 수치·교환 경제는 미구현이다.

## 8. 캐릭터 레벨

정본 범위:

- Lv1~50

성장 원칙:

- HP와 기본 공격력 중심으로 완만하게 성장.
- 사거리, 생산비, 선딜, KB 횟수 등 캐릭터 정체성을 만드는 값은 기본적으로 레벨로 바꾸지 않는다.
- Lv30 이후 성장 기울기는 완화한다.
- 랭크 PvP Lv30 표준화는 후보.
- 레벨 계산은 정수 기반이며 같은 level/form이면 동일한 전투 정의를 만든다.

현재 `content/growth/level-curve-01.json`의 구체 수치는 `PROTOTYPE_BALANCE` 상태다.

현재 프로토타입 곡선:

- Lv1 = 1000‰
- Lv1~30: 레벨당 HP/공격 +15‰
- Lv31~50: 레벨당 HP/공격 +8‰
- Lv30 = 1435‰
- Lv50 = 1595‰

강화 비용 곡선은 골드/콘텐츠 보상 경제와 함께 확정한다.

## 9. 3형태 진화

기본 구조:

1. **기본 형태** — 핵심 역할과 첫 인상.
2. **2형태** — 역할 변화/전문화가 눈에 띄기 시작.
3. **3형태** — 외형과 전투 특성이 본격적으로 변화하는 완성형.

변경 가능 요소:

- 실루엣/체형
- 의상/갑옷/무기/대표 소품
- Idle/Run/Attack/KB/Death
- 소환 연출/투사체/VFX/SFX
- HP/공격력
- 생산비/재생산
- 사거리/사각지대
- SINGLE/AREA
- 멀티히트
- 속성/전문
- 실제 구현된 Push/Slow/Freeze/Weaken/Strengthen/Critical/방어관통 등

원칙:

- 모든 진화가 무조건 상위호환일 필요는 없다.
- sidegrade와 특정 상황 전문화를 허용한다.
- **이전 형태를 다시 선택할 수 있다.**
- form을 바꿔도 같은 캐릭터의 소유권과 레벨을 공유한다.
- 진화 form을 별도 characterId로 다시 뽑게 하지 않는다.
- 색만 바꾸는 진화 금지.
- 아직 전투 코어에 없는 효과를 설명에만 먼저 적어 작동하는 것처럼 만들지 않는다.

현재 C/B/A/S/SS 대표 5명에 각각 3-form 전투 데이터가 있다:

- 순무기수
- 등불마녀
- 태엽오리기사
- 거울퇴마사
- 달먹는룡

form3를 form2보다 먼저 해금하는 순서 건너뛰기는 저장 API에서 거부한다.

진화 요구 레벨/재료 수치는 아직 정본화하지 않았다. 과거 기획에 없던 Lv20/40 같은 숫자를 임의로 넣지 않는다.

## 10. 수동 10칸 덱

초기 전체 기획의 명시적 규칙:

- 솔로/1v1: 10칸.
- 협동/2v2: 플레이어당 5칸, 팀 전체10.
- 전체 보유 캐릭터가 10종 이하인 초기 단계에는 자동 편성을 허용.
- **캐릭터 풀이 10종을 넘으면 수동 10칸 편성이 핵심 메타가 된다.**

현재 전투 정의가 25종이므로 수동 편성은 현재 필수다.

save v6 규칙:

- 명시적 덱은 최소1 / 최대10.
- 같은 캐릭터 중복 배치 금지.
- 실제 보유 캐릭터만 편성 가능.
- 슬롯 순서를 저장하고 PC `1~0` 소환 순서에도 반영한다.
- 기존 저장에서 명시적 덱이 없으면 보유 캐릭터를 정본 순서로 최대10 자동 편성하여 과거 진행을 깨지 않는다.
- 사용자가 한 번 명시적 덱을 저장하면 그 덱이 권위.
- 자동 편성으로 되돌리는 기능은 별도 제공 가능하며 현재 저장 API가 지원한다.

현재 구현:

- save v6의 `deckSlotIds`.
- `recordGuestDeck()`.
- `resetGuestDeckToAutomatic()`.
- `getEffectiveDeckSlotIds()`.
- `player-loadout.ts`에서 저장된 덱 + level + form을 실제 전투 슬롯으로 파생.

아직 미구현:

- 기존 `FormationScene/DeckScene`이 이 API를 사용하는 실제 선택 UI.
- 실제 `BattleScene`이 새 loadout 경로를 소비하는 연결.

따라서 수동덱 전체 기능 상태는 아직 `PARTIAL`이다.

## 11. 저장 모델 — 현재 v6

현재 guest save는 v2~v5에서 v6으로 마이그레이션한다.

현재 저장 대상:

- 메인 클리어 스테이지
- SPECIAL 클리어
- 보물
- 모집 캐릭터 소유권
- 배너별 totalPulls / selectionCredits
- characterId별 level
- characterId별 해금 form 목록
- characterId별 현재 선택 formId
- 명시적 1~10칸 덱

향후 추가:

- characterId별 보유 조각
- 공용 성장 재화
- 모집 재화/모집권
- 골드
- 진화 재료

소유권, 레벨, form, 덱은 서로 다른 책임으로 저장한다.

저장 병합 시:

- 모집 pull 수를 단순 합산하지 않는다.
- 이미 소비한 100연 선택권을 되살리지 않는다.
- 캐릭터 레벨은 높은 정상 진행을 보존한다.
- 해금 form은 합집합.
- 현재 세션의 같은 레벨 form 선택을 우선한다.
- 명시적 덱은 현재 세션 선택을 우선한다.

## 12. 실제 전투 파이프라인

전투 코드는 최종적으로 다음 한 경로를 사용해야 한다.

`GuestProgress`
→ 보유 캐릭터 확인
→ 명시적/자동 deck 결정
→ 캐릭터별 level
→ 현재 선택 form
→ 실제 `BattleUnitDefinition`
→ 보물 효과
→ `createPlayableBattle()`

현재 구현:

- `apps/client/src/player-loadout.ts`
  - `buildGuestDeckSlots(progress)`
  - `createGuestPrototypeBattle(stageId, progress)`
- `prototype.ts`
  - `createPrototypeBattleWithPlayerSlots()`

아직 `main.ts`의 실제 BattleScene이 이 경로를 소비하도록 전환되지 않았다. 이것이 다음 최우선 연결 작업이다.

## 14. 구현 우선순위

이미 완료/진행된 기반:

1. 정밀 모집/성장 기획 복원.
2. 모집 전용15 content.
3. 배너 데이터/모집 엔진.
4. 모집 소유권/천장 저장.
5. Lv1~50 전투 스탯 파생.
6. 대표5명 3-form 데이터/엔진.
7. save v6 level/form/deck 저장.
8. 저장된 deck/level/form → 전투 슬롯 파생 경로.

지금부터 우선:

1. **FormationScene/DeckScene 실제 수동10칸 UI → `recordGuestDeck()` 연결.**
2. **BattleScene → `createGuestPrototypeBattle()` 연결.**
3. 모집 화면/결과 연출.
4. 성장 화면.
5. 골드/모집재화/조각/진화재료 경제 정본화.
6. 중복 조각/교환 구현.
7. form2/3 실제 해금 조건.
8. 전체 캐릭터 3-form 확장.
9. 도감25+와 검색/필터.
10. form별 정식 아트/애니/VFX/SFX.

스테이지 수를 더 늘리기 전에 1~4를 우선한다.

## 15. 금지 사항

- 기본10을 모집 풀에 넣어 캠페인 해금 가치를 훼손.
- 높은 희귀도만 있으면 하위 희귀도가 쓸모없어지는 구조.
- SS를 단순 수치 상위호환으로만 설계.
- 중복 없이는 정상 성능을 못 내는 구조.
- 진화를 새 캐릭터 재획득으로 처리.
- 진화를 색놀이로 처리.
- 아직 없는 전투 효과를 설명만 넣어 구현된 것처럼 표시.
- 모집 확률과 실제 roll 코드가 따로 하드코딩되는 구조.
- UI에서 별도 확률을 다시 계산하는 구조.
- 캐릭터가 10종을 넘었는데 자동 전체편성만 유지.
- level/form을 저장하면서 실제 전투에는 Lv1 기본형만 쓰는 반쪽 구현.
- 모집/성장 백엔드가 있다는 이유로 모집/성장/편성 UI를 무기한 미루기.
